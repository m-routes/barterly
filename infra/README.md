# infra

Everything needed to recreate Barterly's staging and production environments.

| Path | What |
| --- | --- |
| `scripts/bootstrap.sh` | Enables base APIs and creates the Terraform state bucket |
| `terraform/shared/` | APIs, Artifact Registry, GitHub Workload Identity Federation |
| `terraform/modules/environment/` | One environment: service accounts, secrets, buckets, Cloud SQL, Cloud Run `api` + `web`, migrate job |
| `terraform/envs/{staging,production}/` | Roots that instantiate the module |
| `scripts/set-secrets.sh` | Generates the Django secret key into Secret Manager |
| `scripts/deploy.sh` | Candidate revision → migrate job → smoke test → traffic (used by CI) |
| `scripts/rollback.sh` | Moves traffic back to an earlier revision |
| [ROLLBACK.md](ROLLBACK.md) | Rollback runbook |

## Layout in GCP (asia-south1)

Staging and production live in one GCP project, separated by name suffix, service account and IAM. Splitting them into two projects later only means pointing `envs/production` at a different `project_id`.

| Resource | Staging | Production |
| --- | --- | --- |
| Cloud Run service (API) | `barterly-api-staging` | `barterly-api-production` |
| Cloud Run service (web) | `barterly-web-staging` | `barterly-web-production` |
| Cloud Run job (migrations + collectstatic) | `barterly-migrate-staging` | `barterly-migrate-production` |
| Media bucket (private, signed URLs only) | `<project>-media-staging` | `<project>-media-production` |
| Static bucket (public read) | `<project>-static-staging` | `<project>-static-production` |
| Secrets | `django-secret-key-staging`, `database-url-staging` | same with `-production` |
| Cloud SQL (PostgreSQL 16) | `barterly-staging`: `db-f1-micro`, zonal, 7 backups | `barterly-production`: `db-custom-1-3840`, regional (HA), 30 backups |
| API max instances | 2 | 10 |
| Min instances | 0 | 1 |

### Service accounts (least privilege)

| Account | Can do |
| --- | --- |
| `barterly-api-<env>` | Read its secret key and DB URL; connect to Cloud SQL (`cloudsql.client`); read/write objects in its media bucket; sign blobs as itself (for signed URLs) |
| `barterly-web-<env>` | Nothing. The web server holds no secrets |
| `barterly-migrate-<env>` | Read its secret key and DB URL; connect to Cloud SQL (`cloudsql.client`); write objects in its static bucket |
| `barterly-deploy-<env>` | Used by GitHub Actions in the matching GitHub environment only. `run.developer` on its own two services and job, `run.viewer` on the project, actAs on the three runtime accounts, Artifact Registry **writer** (staging) or **reader** (production: it can only promote) |

There are no service account keys. GitHub authenticates through Workload Identity Federation, restricted to this repository, and each deployer account accepts only tokens from its own GitHub environment (`attribute.environment`).

### Database (Cloud SQL)

- One Cloud SQL for PostgreSQL 16 instance per environment, in asia-south1 next to Cloud Run, so data stays in India.
- **Access:** the instance has a public IP with no authorized networks. The API and the migrate job reach it only through Cloud Run's built-in Cloud SQL connector, a Unix socket mounted at `/cloudsql`. The connector checks IAM (`roles/cloudsql.client`) and encrypts traffic. Any direct TCP connection must use TLS (`ssl_mode = ENCRYPTED_ONLY`). `sslmode=require` applies only to TCP hosts.
- **Password:** generated by an ephemeral `random_password` and passed only to write-only arguments (`password_wo`, `secret_data_wo`), so it never lands in Terraform state, plans or git. To rotate, bump `db_password_version`, apply, then redeploy.
- **Pooling:** each gunicorn worker has its own psycopg pool, from Django's built-in pooling, of at most `DB_POOL_MAX_SIZE` connections (default 4), with `CONN_MAX_AGE=0`. Keep `api_max_instances × api_workers × db_pool_max_size` + 2 (for the migrate job) under the tier's `max_connections`: about 25 on `db-f1-micro` and 100 on `db-custom-1-3840`.
- **Retries:** the custom DB backend (`apps.core.db.postgresql`) retries new connections with backoff (0.5s, 1s, 2s; 4 attempts) and a 10s `connect_timeout`, so requests survive brief restarts during maintenance or failover.
- **Maintenance:** Sundays at 21:00 UTC (02:30 IST). **Backups:** daily at 02:00 IST, plus point-in-time recovery with 7 days of logs.

## Recreate from scratch

Prerequisites: `gcloud` (logged in as a project owner), Terraform ≥ 1.11, `openssl`.

```bash
export PROJECT_ID=barterly-prod-123456
export STATE_BUCKET=${PROJECT_ID}-tfstate
```

1. Bootstrap the project and state bucket.

```bash
infra/scripts/bootstrap.sh
```

2. Shared resources (Artifact Registry, Workload Identity Federation).

```bash
cd infra/terraform/shared
cp terraform.tfvars.example terraform.tfvars   # edit project_id, github_repository
terraform init -backend-config="bucket=${STATE_BUCKET}"
terraform apply
cd -
```

3. Secret containers for each environment first. Cloud Run can't start a revision that references a secret with no versions.

```bash
for env in staging production; do
  (cd infra/terraform/envs/$env && cp -n terraform.tfvars.example terraform.tfvars &&
   terraform init -backend-config="bucket=${STATE_BUCKET}" &&
   terraform apply -target='module.environment.google_secret_manager_secret.this')
done
```

4. The Django key for each environment. `DATABASE_URL` is written by Terraform in the next step.

```bash
infra/scripts/set-secrets.sh staging
infra/scripts/set-secrets.sh production
```

5. Everything else: Cloud SQL (the first create takes about 10 minutes), the database URL secret, service accounts, buckets, the Cloud Run services and job, and IAM.

```bash
(cd infra/terraform/envs/staging && terraform apply)
(cd infra/terraform/envs/production && terraform apply)
```

6. GitHub. Create environments `staging` and `production`. On `production`, add required reviewers and limit deployments to tags matching `v*.*.*`. Set these **variables** (not secrets; none of them are sensitive) on each environment:

| Variable | Source |
| --- | --- |
| `GCP_PROJECT_ID` | your project id |
| `GCP_PROJECT_NUMBER` | `terraform output` → `environment.project_number` |
| `GCP_WIF_PROVIDER` | `terraform output workload_identity_provider_name` (shared) |
| `GCP_DEPLOY_SA` | `terraform output` → `environment.deploy_service_account` |
| `WEB_URL` | `terraform output` → `environment.web_run_url` (or your domain) |

Also protect `main` so merges need the backend, web and infra checks to pass. Deploys run on merge and don't re-run CI.

7. Deploy. Merge to `main` to deploy staging. Tag a commit that staging is running and push the tag to deploy production after approval:

```bash
git tag v0.1.0 && git push origin v0.1.0
```

Custom domains: add them to `api_domains` / `web_domains` in `terraform.tfvars` (this updates `ALLOWED_HOSTS`, CSRF origins and bucket CORS), apply, then map them with a global HTTPS load balancer or Cloud Run domain mapping.

## How a deploy works

`infra/scripts/deploy.sh <env> <sha>`:

1. Deploys the API image as a new revision with **no traffic**, tagged `candidate`.
2. Points the migrate job at the same image and runs `python manage.py release` (`migrate` + `collectstatic`), waiting for it to finish. A failed migration stops the deploy, and the old revision keeps serving.
3. Smoke-tests `https://candidate---barterly-api-<env>-<project number>.asia-south1.run.app/api/v1/health/`.
4. Moves 100% of traffic to the new revision, then does the same candidate → smoke → traffic flow for web.

Because the old revision serves while migrations run, migrations must be backwards compatible with the previous release (expand, deploy, then contract in a later release). See CONTRIBUTING.md.

Production never builds. It promotes the `api:<sha>` and `web:<sha>` images that staging already ran, and fails if they don't exist.
